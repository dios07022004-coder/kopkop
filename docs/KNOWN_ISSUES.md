# Ошибки и недочёты — анализ системы

> Полный разбор расчётов, ввода и UX. Что исправлено и что осталось. Обновляй по мере правок.

## ✅ Исправлено (последние правки)
1. **«Кабинет» открывал калькулятор** — в шапке ссылка вела на `/app`. → `/account`. Кнопка «Файлы» на калькуляторе → «Кабинет».
2. **«В день» скакал под конец месяца** — было `остаток / оставшиеся дни` (под конец месяца давало 15 000/день). → календарный месяц: устойчивая норма `свободно / дней_в_месяце`; цикл (день зарплаты): `остаток / дней до ЗП`.
3. **Нереалистичный расчёт покупки** — «накопить за 2 мес» = откладывать весь бюджет «на жизнь». → теперь: «можно сейчас» если хватает наличных (счёт − подушка); «за N мес» = недостача ÷ реальная сумма откладывания.
4. **Не сохранялся шаблон после расчёта** — в результате квиза добавлена «Сохранить и открыть кабинет»; кабинет показывает аналитику по сохранённому шаблону.
5. **Дублирование формы** после квиза (квиз + повторная PlanInputs) — убрано.
6. **CTA только Telegram** — теперь «Приложение И Telegram» (фокус на приложении), бюджет синхронизируется.
7. **Покупка не отображалась в кабинете** — добавлена карточка «🛒 Покупка X — не хватает Y, накопите за N мес».
8. **Откладывание больше свободного** — теперь предупреждение в результате квиза с рекомендацией.
9. **CSS не грузился / 502** — причина: `rm -rf .next` + `pm2 restart` до завершения `build` (крэш-цикл «no production build»). Правильный порядок: `pm2 stop` → `rm -rf .next` → `npm run build` (ждать ✓) → `pm2 start`.
10. **Тёмная тема** внедрена на весь сайт (палитра `.dark`, аудит хардкод-цветов).

## ⚠️ Известные недочёты / ограничения (требуют решения)

### Расчёт
- **A. Календарный месяц не знает реальных трат.** Если день зарплаты не указан, «осталось» = свободно − записанные траты, а уже потраченное за месяц до начала ведения леджера не вычитается. **Решение для пользователя:** указывать день зарплаты (режим cash-flow от остатка на счёте) или вести траты с 1-го числа. Фундаментально без банковской интеграции точнее не сделать.
- **B. Покупка/накопления зависят от честности ввода «откладываю в месяц».** Если 0 — срок до покупки не считается (просим указать). Это правильно, но пользователь может не понять.
- **C. Леджер растёт по дням** — старые записи не удаляются (агрегация по периоду от `fromDay`). Не критично, но со временем стоит архивировать.

### Платежи / монетизация
- **D. Вебхук YooKassa без IP-allowlist** (проверка суммы и переспрос статуса у API есть). Перед массовыми продажами — добавить allowlist. Главный блокер.
- **E. Нет подписки (рекуррента).** На разовых 399 ₽ реклама не окупается — нужен LTV (199–299/мес).
- **F. Нет аналитики воронки** (посчитал → оплатил → вернулся) — нельзя оптимизировать рекламу.

### Инфраструктура
- **G. Supabase бесплатный (Ирландия)** — риск авто-паузы через 7 дней и блокировок из РФ. Опция: self-hosted Supabase на сервере.
- **H. Нет rate-limit на API, нет мониторинга/алертов** (если упадёт — узнаете от пользователей).
- **I. Подтверждение email отключено** — регистрация без кода (норм на старте, но любой email можно занять).
- **J. Деплой ломает прод при неверном порядке** — задокументирован безопасный порядок (см. п.9).

### UX / мелочи
- **K. iOS push** работает только из установленного PWA (подсказано на `/install`).
- **L. «Показать детали»** — продвинутые разделы во вкладках (по одной), не «всё сразу». На мобиле всё доступно переключением вкладок.
- **M. `PlanInputs` — мёртвый код** (после перехода на квиз не рендерится). Можно удалить.
- **N. Числовые поля**: отрицательные/мусор нормализуются (clamp ≥ 0), но в квизе ввод `-100` покажет `0` — безопасно, но неинтуитивно.

## Приоритеты (рекомендация)
1. Безопасность вебхука YooKassa (D) — перед продажами.
2. Подписка (E) + аналитика воронки (F) — для окупаемости рекламы.
3. Стабильность инфраструктуры: self-hosted Supabase (G), rate-limit/мониторинг (H).
4. Допилить UX: предупреждения по краевым вводам, удалить мёртвый код (M).
